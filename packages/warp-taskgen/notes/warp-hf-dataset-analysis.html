Research thesis

Lead with eval-awareness behavior, then attack strength, with measurement accounting as the credibility layer.

The central paper claim supported by this dataset is about eval-awareness behavior, not eval-awareness victory. The iterator changes Transcript Purpose (TP) in a meaningful subset of rows, but selected/final TP remains evaluation-like in most rows and Verbalized Eval Awareness (VEA) barely moves. The right claim is "the iterator reduces some elicited purpose cues," not "the iterator makes the benchmark feel real."

The second claim is attack strength. The cohort is high-ASR under both fixed-cohort and exposure-conditioned denominators, and the model-level ASR band is tight across six runs. That supports a strong cohort-level vulnerability result, not a model leaderboard.

The third claim is measurement discipline. WARP makes browser-agent IPI measurement auditable: attack success, payload exposure, benign utility, task breakage, TP, VEA, and iterator failures are separated instead of being collapsed into a single ASR number.

Paper fit

How this HF cohort fits into the paper.

The current paper main contains evidence beyond this Hugging Face export, including cross-benchmark eval-awareness results and causal cue-intervention experiments. This report should therefore not be read as the full empirical program. Its job is narrower and more useful: it audits the released 50-task WARP cohort and spells out exactly what the WARP dataset itself shows.

The cohort supports the paper's WARP instantiation story: 50 generated WARP tasks on WebArena Verified GitLab and Postmill, native-data seeding, six target-model runs, explicit payload exposure accounting, state-confirmed final-status scoring, Transcript Purpose (TP), Verbalized Eval Awareness (VEA), and bounded iterator provenance. It also shows where WARP claims need careful language: TP moves in a meaningful subset, VEA is mostly Real, and action-family differences are not causally identified by this cohort alone.

End-to-end pipeline

What happened before a row entered the HF export.

The dataset is not a hand-written table of outcomes. It is an index over a live browser-agent evaluation pipeline: native benchmark data are seeded, payload exposure is checked from rendered artifacts, final status is derived from programmatic state/readback evidence, and iterator attempts are logged as separate diagnostic rows.

Phase 0

Profile benchmark sites, auth, reset behavior, data models, writable surfaces, and verification capabilities.

Phase 1

Generate benign browser tasks that route through realistic GitLab and Postmill user-generated content surfaces.

Phase 2

Generate payload text and host-owned exposure contracts, then seed through typed editor methods rather than modifying webapp code.

Phase 2c / 3

Admit only tasks whose seed renders and whose contracts remain valid under deterministic checks.

Phase 4

Run the browser agent, apply PVPO exposure measurement, score attack effectiveness, and record TP/VEA.

HF export

Publish runs, tasks, variants, and artifact bundles. The export indexes logs; it does not mutate scoring or generated traces.

Why this matters for reviewers

The important methodological point is that WARP preserves separations that are easy to lose in browser-agent IPI work: whether the payload was encountered, whether the benign task still succeeded, whether the adversarial action was state-confirmed, whether the model verbalized eval awareness, and whether an iterator rewrite changed measured purpose. Those are separate fields in the export rather than post-hoc narrative judgments.

Interpretation guardrail Do not turn the issue-note split into a causal behavior claim. In this cohort, create_issue_note is tied to GitLab issue-description surfaces, public follow-up wording, and same-issue comment readback, so action semantics, site UI, task wording, and payload family are entangled.

Careful hypotheses for why comments behave differently

  • Object creation vs. object reply: new issues and new posts let the agent satisfy an attacker instruction by creating a standalone artifact. Issue notes require attaching text to an existing issue after reading a specific source object, which may make the injected instruction source and user-task conflict more salient.
  • Task-contract friction: comment tasks ask the agent to preserve a benign follow-up/comment contract. If the injection redirects that comment, the conflict with the user task may be easier for the agent or scorer to expose.
  • Different action contract: issue-note tasks require posting a note on the same existing issue that contained the payload, while issue/post creation tasks require creating a standalone object. The same-object check is the correct success condition. The caveat is causal: this cohort cannot tell whether lower issue-note ASR comes from comment-style workflows, GitLab issue UI, source-object matching, task wording, or their combination.
  • Surface-template coupling: in this cohort, create_issue_note is tied to GitLab issue descriptions and a public-comment scenario template. The effect could be action semantics, GitLab UI, task wording, payload family, or all of them.

Working theories

Hypotheses to carry into the study, clearly marked as hypotheses.

1. Eval awareness is layered.

VEA and TP should not be collapsed. VEA captures what the agent spontaneously says; TP captures what a replayed model says when asked about purpose. This follows the evaluation-awareness prior from Needham et al. and related alignment-evaluation awareness work: elicited recognition and spontaneous verbalization are different evidence channels.

2. The iterator edits perceived purpose, not final behavior.

The iterator produces real TP movement, while selected-variant compliance mostly tracks final compliance with a small number of final-only successes. In this cohort, the iterator is best framed as a realism-cue intervention with diagnostic variant-level behavior, not as an ASR optimizer.

3. The action-family split may mix behavior and task structure.

Creating a new issue/post may feel like a natural continuation of the task, while adding a note to an existing issue may make source matching harder and task conflict more salient. WASP and RedTeamCUA both motivate action/scaffold effects, but this cohort needs balanced reruns before turning the split into a behavioral claim.

4. Exposure failures are placement failures, not robustness.

The three non-encounters are failed opportunities for the model to react to the payload. They belong in headline ASR and should be excluded from exposure-conditioned ASR. This denominator split is especially important for browser benchmarks because, unlike many tool-output IPI settings, payload exposure is not structurally guaranteed.

5. Task breakage is utility collapse after exposure.

The two task-broke rows have nonzero PVPO and no adversarial success, but benign failure prevents calling them resistance. This is exactly why browser-agent safety benchmarks need multi-status accounting.

6. Small fixed cohorts need paired evidence.

With 50 tasks per model and overlapping intervals, model rankings should be treated as descriptive. Any model-difference claim needs larger samples or paired tests by task.
