# vLLM 0.16.0 → 0.23.0 numerics review — 2026-08-17

## Verdict

**Yes — three things changed that can move a number, and this tree takes the
default on all three.** None of them is a sampling *default*, which is where the
question naturally points and where the answer is clean: vLLM's sampling
parameter defaults did not change at all. The exposure is one layer down, in the
kernels.

1. **Cascade attention was on by default at 0.16.0 and is off by default from
   0.18.0** ([#36318](https://github.com/vllm-project/vllm/pull/36318)). vLLM's
   own stated motivation is "to avoid potential numerical issues by default".
   The serve scripts never set this flag, so this tree takes the default and the
   default moved underneath it. **Affects both models.**
2. **The top-k/top-p sampler changed backend** — to a Triton kernel at 0.17.0
   (no opt-out) and then to FlashInfer by default at 0.21.0. **Affects GUI-Owl
   only**, because it runs with `top_k=40` and `top_p=0.95` active on every
   request — not because the runners set them, but because vLLM reads them out
   of the model's `generation_config.json`.
3. **The Qwen3-VL vision tower's position-embedding computation was replaced by
   a fused Triton kernel** at 0.19.0
   ([#37948](https://github.com/vllm-project/vllm/pull/37948)), collapsing ~25
   eager ops into one. Default-on, no flag. **Affects GUI-Owl only.**

All three are floating-point-level changes to a mathematically equivalent
computation. They do not make the server wrong. They mean a value can land on
the other side of a boundary, and at `temperature=0.1` — this tree's default,
with no `seed` sent — that is enough to change a sampled token, a tool call, and
therefore a judged outcome.

`xlangai/OpenCUA-32B` is materially *less* exposed than GUI-Owl, for a reason
worth stating precisely: it ships no sampling parameters in its
`generation_config.json`, so top-k/top-p filtering is disabled for it entirely
and the sampler-kernel change cannot reach it. Of the exposures below, only A1
reaches OpenCUA — plus one unresolved question about its inherited Qwen2.5-VL
vision tower (B7).

Three things a shorter answer would have gotten wrong, and which the detail
below exists to establish:

- **Sampling *defaults* did not change.** Every value in `SamplingParams` is
  identical at both tags, and the mechanism that reads a model's
  `generation_config.json` is byte-identical. The natural place to look for this
  risk is clean; the risk is one layer below it.
- **The Model Runner V2 rollout — the loudest numerics story in the release
  notes — does not touch either model.** Its default architecture allow-list is
  text-only (`{LlamaForCausalLM, MistralForCausalLM, Qwen3ForCausalLM}`); both
  served models are vision-language and stay on the V1 runner.
- **The one large, quantified accuracy regression in the window is interior to
  it.** vLLM shipped a ~30% relative Qwen3-VL accuracy drop at 0.20.0 and fixed
  it at 0.23.0 (finding D). Both *endpoints* of this upgrade are clean — but
  anything pinned in between is not, and any GUI-Owl result collected on
  0.20.0–0.22.1 is suspect.

**Recommendation: pin `vllm` and `transformers`, audit the run log, then measure
GUI-Owl once on GPU.** The upgrade to 0.23.0 is not the danger; the unpinned
`vllm>=0.6` that let it happen unreviewed is, and it now points at releases that
break this tree outright. See [Recommendation](#recommendation).

## What actually moved

`pyproject.toml:100` declares `vllm>=0.6`, which pins nothing. The lockfile is
what moved, and it moved as a side effect.

Before #172, `uv.lock` carried a **fork**:

```
{ name = "vllm", version = "0.16.0", marker = "python_full_version < '3.13'" }
{ name = "vllm", version = "0.23.0", marker = "python_full_version >= '3.13'" }
```

#172 narrowed `requires-python` from `>3.10` to `>=3.12,<3.13`, collapsing the
fork to a single `{ name = "vllm" }` at **0.23.0**.

The consequence is the one that matters: **`.python-version` pins `3.12`**, so
the branch this project actually runs previously resolved to **vLLM 0.16.0**.
Every `uv pip install -e '.[cua]'` on the supported interpreter now gets
0.23.0. This is a real seven-minor-version jump for every `cua` host, not a
theoretical one.

The default profile is genuinely unaffected. Verified in the built worktree
environment: `vllm` is **absent**, while `torch` and `transformers` are present.

## How this tree actually calls vLLM

This is the fact that collapses most of the release-note surface, and it should
be stated before any of the findings.

**No first-party code imports `vllm`.** A repo-wide search for `import vllm` /
`from vllm` outside the vendored `AgentLab/` tree returns nothing. vLLM is used
only as a **server binary** (`vllm serve`), reached over an OpenAI-compatible
HTTP endpoint.

Every Python-API change in the window is therefore irrelevant here — the
`get_tokenizer` / `resolve_hf_chat_template` relocations
([#35024](https://github.com/vllm-project/vllm/pull/35024)), the `LLM.reward`
deprecation, the `SamplingParams` construction path. None of it is on this
tree's path.

What *is* on the path:

- **`models/common/vllm_client.py`** builds an `AsyncOpenAI` client. It imports
  `openai`, not `vllm` (`vllm_client.py:21`).
- **`eval_awareness_experiments/tool_calling_runner.py:265-272`** is the real
  request. It sends exactly:

  ```
  model, messages, tools, max_tokens=self.max_tokens, temperature=self.temperature
  ```

  **No `top_p`. No `top_k`. No `seed`.** `max_tokens` defaults to 8192 and
  `temperature` to 0.1 (`tool_calling_runner.py:154-155`).
- **`AgentLab`'s `VLLMChatModel`** (`AgentLab/src/agentlab/llm/chat_api.py:466`)
  likewise passes only `temperature` and `max_tokens`.
- **The serve scripts** (`models/opencua/serve_32b.sh:32-41`,
  `models/opencua/serve_72b.sh`, `models/gui_owl/serve_32b.sh:21-30`) pass:
  `--tensor-parallel-size 1 --gpu-memory-utilization 0.92 --max-model-len 32768
  --dtype bfloat16 --trust-remote-code --enable-auto-tool-choice
  --tool-call-parser hermes`.

Two consequences follow directly:

1. **`temperature` and `max_tokens` are set explicitly on every request**, so
   this tree is insulated from any change to *their* defaults.
2. **`top_p` and `top_k` are never set**, so whatever the server defaults them
   to is what runs. That is the seam the exposure comes through.

`probes/` is outside the blast radius entirely. It loads models through HF
`transformers` (`probes/train_probe.py:364` → `models/common/hf_loader.py`),
never through vLLM, with `--dtype` defaulting to `bfloat16`
(`probes/train_probe.py:322`). `models/common/hf_openai_server.py` is a
first-party HF-backed OpenAI-shaped server and does not involve vLLM either.

### Where top-k and top-p actually come from

vLLM's `--generation-config` defaults to `"auto"`, which means it reads the
model's own `generation_config.json` and uses it to supply server-side default
sampling parameters. Verified in source at **both** tags:

- `vllm/config/model.py:259` at
  [v0.16.0](https://github.com/vllm-project/vllm/blob/v0.16.0/vllm/config/model.py)
  — `generation_config: str = "auto"`
- `vllm/config/model.py:285` at
  [v0.23.0](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/config/model.py)
  — `generation_config: str = "auto"`

`ModelConfig.get_diff_sampling_param()` is **byte-identical** between the two
tags. It lifts exactly these keys out of the model's config:

```python
available_params = [
    "repetition_penalty", "temperature", "top_k", "top_p", "min_p",
    "max_new_tokens",
]
```

Now the two served models diverge sharply:

| | `xlangai/OpenCUA-32B` | `mPLUG/GUI-Owl-1.5-32B-Think` |
| --- | --- | --- |
| `generation_config.json` | `{"max_length": 32768, "eos_token_id": 151644}` | `{"do_sample": true, "temperature": 0.6, "top_k": 40, "top_p": 0.95, …}` |
| Sampling params injected | **none** | `temperature`, `top_k`, `top_p` |
| Effective `top_p` | `1.0` (vLLM neutral default) | **`0.95`** |
| Effective `top_k` | `0` = disabled | **`40`** |
| Top-k/top-p kernel exercised? | **No** | **Yes, every request** |

Both fetched from the HuggingFace `raw/main` endpoint on 2026-08-17.

Note that `max_length` is **not** in `available_params` — only `max_new_tokens`
is. So OpenCUA's `max_length: 32768` is never read as a `max_tokens` default,
and the client's explicit `max_tokens=8192` governs unopposed.

## Findings

### A. Changed, and this tree is exposed

#### A1. Cascade attention default flipped `False` → `True`

[PR #36318](https://github.com/vllm-project/vllm/pull/36318), merged
2026-03-11, shipped in **v0.18.0**. Verified in source at both tags:

| Tag | `vllm/config/model.py` | Value |
| --- | --- | --- |
| v0.16.0 | line 218 | `disable_cascade_attn: bool = False` |
| v0.23.0 | line 246 | `disable_cascade_attn: bool = True` |

The PR body states the motivation without hedging:

> Make cascade attention opt-in to avoid potential numerical issues by default,
> requiring users to explicitly enable it.

And the docstring, present verbatim in both versions, is explicit about what
kind of change this is:

> While cascade attention does not change the mathematical correctness,
> disabling it could be useful for preventing potential numerical issues.

That is the exact signature of a finding that matters here: mathematically
equivalent, numerically different. Cascade attention splits attention into a
shared-prefix pass and a suffix pass and merges them, which changes the
floating-point reduction order relative to the unified path.

**Why this tree is exposed.** None of the three serve scripts passes
`--disable-cascade-attn`, so all three take the default. At 0.16.0 the
heuristic could select cascade attention; from 0.18.0 it cannot without an
explicit opt-in. The heuristic fires on long shared prefixes across concurrent
requests — which is precisely this workload's shape, since every task in a
condition shares a system prompt and injection frame.

**Direction:** 0.23.0 is the safer configuration. vLLM removed a path it
considered numerically risky. But results produced under 0.16.0 may have been
computed through that path, and results produced now will not be.

I could **not** determine how often the heuristic actually fired for these
specific workloads — that requires instrumented runs on GPU hardware. See
[Gaps](#what-i-could-not-determine).

#### A2. The top-k/top-p sampler changed three times — GUI-Owl only

This is the finding with the sharpest edge, and it applies to **exactly one of
the two served models**.

Because `mPLUG/GUI-Owl-1.5-32B-Think` ships `top_k: 40` and `top_p: 0.95` in its
`generation_config.json`, and `--generation-config` defaults to `auto`, every
GUI-Owl request arrives at the sampler with top-k and top-p **active** — even
though no runner ever sets them. That puts it on the changed path. Three
changes stack:

| PR | Release | What changed | Gated? |
| --- | --- | --- | --- |
| [#33538](https://github.com/vllm-project/vllm/pull/33538) | v0.17.0 | Top-k/top-p masking moves from exact sort-based to a **Triton pivot-search** kernel, for any batch of **≥ 8 rows** | **No opt-out** |
| [#37225](https://github.com/vllm-project/vllm/pull/37225) | v0.19.0 | Alters that kernel's pivot search (`min_larger` / `num_min_larger` semantics), changing which pivot is accepted | **No opt-out** |
| [#40376](https://github.com/vllm-project/vllm/pull/40376) | v0.21.0 | **FlashInfer sampler enabled by default** — rejection sampling replaces Gumbel-max | `VLLM_USE_FLASHINFER_SAMPLER` |

For #40376 the default flip is verifiable in one line, in `vllm/envs.py`:

| Tag | Declaration | Effect |
| --- | --- | --- |
| v0.16.0 (line 48) | `VLLM_USE_FLASHINFER_SAMPLER: bool \| None = None` | falsy → opt-**in** |
| v0.23.0 (line 50) | `VLLM_USE_FLASHINFER_SAMPLER: bool = True` | on by **default** |

And vLLM does not claim the two agree. The docstring on `flashinfer_sample` at
v0.23.0 says so directly:

> NOTE: The outputs of this function do not necessarily match the outputs of
> the `random_sample` function. It only guarantees that the outputs are
> statistically equivalent.

"Statistically equivalent" is the correct guarantee for a serving engine and
the wrong one for a reproducible measurement. For a benchmark that scores
individual trajectories, a different token stream is a different trajectory.

vLLM's own CI records the flip: #40376 amended
`.buildkite/test_areas/samplers.yaml` with the note that the variable "defaults
to 1 now, so we need to pin both values explicitly to still cover the
PyTorch-native (Triton) path."

**Two properties of the dispatch matter for how this is mitigated.**

*First, the decision is per-batch, not per-request.* `k` and `p` reach the
sampler as batch-wide tensors, and are `None` only when **no** request in the
batch sets them (`no_top_p` / `no_top_k` in
`vllm/v1/worker/gpu_input_batch.py`). One co-scheduled request with `top_p < 1`
pulls the whole batch onto the FlashInfer path. For a dedicated
single-model server — which is what the serve scripts stand up, one model per
port — the batch is homogeneous, so this is contained. It would stop being
contained on a shared server.

*Second, the Triton masking kernel from #33538/#37225 has no flag at all.* It is
conditioned only on `HAS_TRITON` and `logits.shape[0] >= 8`. Setting
`VLLM_USE_FLASHINFER_SAMPLER=0` recovers the pre-0.21.0 *sampler*, but **not**
the pre-0.17.0 *masking*. That residual delta cannot be configured away; only a
version pin or a code patch removes it.

**Greedy is safe.** At `temperature=0`, `all_greedy` returns before the sampler
is reached, and in mixed batches the FlashInfer result is overwritten per row by
`torch.where(temperature < _SAMPLING_EPS, greedy_sampled, random_sampled)`. The
paths in this tree that pass `temperature=0.0` —
`eval_awareness_experiments/run_safety_pipeline.py:1383` and `:1853`,
`wasp_post_hoc_evaluator.py:418` — are therefore unaffected by A2. The default
`temperature=0.1` path is not.

#### A3. The Qwen3-VL vision tower's position-embedding kernel — GUI-Owl only

[PR #37948](https://github.com/vllm-project/vllm/pull/37948), "[Perf] triton
bilinear_pos_embed kernel for ViT", merged 2026-04-01, shipped in **v0.19.0**.
From the PR body:

> Add a fused Triton kernel for bilinear position embedding interpolation in ViT
> (`Qwen3_VisionTransformer`). This replaces ~25 small eager-mode CUDA kernel
> launches (linspace, meshgrid, indexing, multiply, sum, reshape, permute) with a
> single fused GPU kernel that performs bilinear interpolation with
> spatial-merge reordering baked into the index math.

Two properties make this an exposure rather than a curiosity:

1. **It is default-on.** The PR states "All four Qwen3 VL model variants benefit
   automatically since they share the same `Qwen3_VisionTransformer` class", and
   the PyTorch fallback (`pos_embed_interpolate_native`) is used only "when
   Triton is unavailable". Triton is present in any working CUDA install.
2. **Collapsing ~25 separate ops into one fused kernel changes the
   floating-point accumulation and rounding order.** The PR ships accuracy tests
   (`tests/kernels/core/test_vit_bilinear_pos_embed.py`), but accuracy tests of
   this kind assert closeness within tolerance, not bit-equality.

GUI-Owl is a `Qwen3VLForConditionalGeneration` and therefore uses
`Qwen3_VisionTransformer`. Its position embeddings are computed by a different
kernel at 0.23.0 than at 0.16.0, on the default path, with no flag to revert.

**OpenCUA is not affected** — it inherits the *Qwen2.5*-VL vision tower, a
different class, and the Qwen2.5-VL attention changes that did land are opt-in
(B7).

We have **not** quantified the magnitude of this one. It is a vision-encoder
input perturbation rather than a sampling change, so it propagates through the
whole forward pass; whether it survives to change a sampled token is exactly the
kind of question the GPU measurement in the recommendation would answer.

### B. Changed, and this tree is insulated

#### B1. The whole Model Runner V2 line — neither model is eligible

MRv2 collected four numerics changes in the window:

| PR | Release | Change |
| --- | --- | --- |
| [#37798](https://github.com/vllm-project/vllm/pull/37798) | v0.19.0 | FP64 Gumbel noise (ungated at the time) |
| [#37526](https://github.com/vllm-project/vllm/pull/37526) | v0.19.0 | Draft logits held at fp32 rather than model dtype |
| [#41775](https://github.com/vllm-project/vllm/pull/41775) | v0.22.0 | Reverts the above default — FP32 Gumbel, `--use-fp64-gumbel` defaults `False` |
| [#42472](https://github.com/vllm-project/vllm/pull/42472) | v0.23.0 | FlashInfer sampler on the MRv2 path |

**None of them reaches this tree**, because MRv2 auto-activates only for an
allow-list of architectures. At v0.23.0, `vllm/config/vllm.py`:

```python
DEFAULT_V2_MODEL_RUNNER_ARCHITECTURES = frozenset(
    {
        "LlamaForCausalLM",
        "MistralForCausalLM",
        "Qwen3ForCausalLM",
    }
)
```

The served architectures are `OpenCUAForConditionalGeneration` (from
`xlangai/OpenCUA-32B`'s `config.json`) and `Qwen3VLForConditionalGeneration`
(from `mPLUG/GUI-Owl-1.5-32B-Think`). Neither is in the set — note that the
entry is `Qwen3ForCausalLM`, the **text-only** dense model, not the VL variant.
Both models stay on the V1 model runner, exactly as at 0.16.0.

(#37526 is doubly inapplicable: it only allocates when `cache_draft_logits` is
set, and this tree does not use speculative decoding.)

#### B2. The sampler changes do not reach OpenCUA-32B

`xlangai/OpenCUA-32B`'s `generation_config.json` contains no sampling
parameters, so every request against it carries vLLM's neutral defaults
`top_p=1.0` and `top_k=0`. Neither qualifies as "set" —
`gpu_input_batch.py` admits a request to `top_p_reqs` only if
`sampling_params.top_p < 1`, and to `top_k_reqs` only if
`0 < top_k < vocab_size`. So `k` and `p` are `None` for the whole batch, and
`forward_cuda` short-circuits:

```python
if (k is None and p is None) or generators:
    return self.forward_native(logits, generators, k, p)
```

`apply_top_k_top_p` then returns the logits untouched, and sampling is plain
`random_sample`. **The Triton masking kernel and the FlashInfer sampler are
both bypassed** — A2 does not apply to OpenCUA at all.

A line-by-line comparison of that surviving native path across the two tags
(v0.16.0: `q = torch.empty_like(probs); q.exponential_(); probs.div_(q).argmax(...)`;
v0.23.0: `sample_with_exponential_noise` taking its `q.dtype == probs.dtype`
branch to the same `probs.div_(q).argmax(...)`) shows the same dtype, shape,
fill order, and arithmetic, on contiguous `probs` straight out of `softmax`.
**Assessed as bit-identical given identical RNG state.** Flagging that clearly:
this is our reading of the two implementations, **not an upstream guarantee**,
and it has not been measured on hardware.

#### B3. `temperature` and `max_tokens` are always set explicitly

Both are passed on every request (`tool_calling_runner.py:269-270`), so no
change to their defaults could reach this tree. This is the reason
[#34063](https://github.com/vllm-project/vllm/pull/34063) (v0.17.0,
"`generation_config` max_tokens treated as default not ceiling") is not a
hazard here, and it is doubly moot for OpenCUA: `get_diff_sampling_param()`
reads `max_new_tokens`, not `max_length`, and OpenCUA's config only has the
latter.

#### B4. ROCm and CPU sampler changes — wrong platform

[#43331](https://github.com/vllm-project/vllm/pull/43331) (v0.23.0) re-enables
the AITER top-k/top-p sampler on ROCm, and
[#43633](https://github.com/vllm-project/vllm/pull/43633) (v0.23.0) routes CPU
top-k/top-p through Triton. This project's hosts are A100/H100 NVIDIA
(`docs/HANDOFF_GUI_OWL_PROBE_RESULTS.md`), so neither path is taken.

Worth recording because the release note is misleading: despite the PR titled
"Enable the aiter top-k/top-p sampler **by default**", the merged diff is a
4-line deletion that adds no env var, and the actual gate is the pre-existing
`VLLM_ROCM_USE_AITER`, which **defaults to `False`** in `vllm/envs.py` at
v0.23.0. The PR body describes a `VLLM_ROCM_USE_AITER_SAMPLER` variable that
does not exist in the merged code. Do not propagate that claim.

#### B5. Pooling non-determinism — no pooling here

[#37775](https://github.com/vllm-project/vllm/pull/37775) (v0.19.0) fixed
genuine run-to-run non-determinism in pooling metadata caused by pinned-memory
aliasing. It affects pooling/embedding/reranking outputs only, never a
generation token stream. This tree runs no pooling or embedding requests
through vLLM.

#### B6. The Hermes tool parser — rewritten, but only on the streaming path

All three serve scripts pass `--tool-call-parser hermes`, so this parser is
directly on the path. It was rewritten in
[#38168](https://github.com/vllm-project/vllm/pull/38168) (v0.19.0, "Fix Hermes
tool parser when stream interval > 1"), which replaced per-chunk
`partial_json_parser` reconstruction with full re-parse plus string diffing.
That **can** change how a tool call assembles — the old code had a
`delta_text.rindex('"}')` close-out path and a
`encode("utf-8").decode("unicode_escape")` branch that are now gone.

**It does not reach this tree, for a checkable reason.** The rewrite is confined
to `extract_tool_calls_streaming`. The non-streaming `extract_tool_calls` is
**byte-identical** between v0.16.0 (lines 124-175) and v0.23.0 (lines 69-120) of
`vllm/tool_parsers/hermes_tool_parser.py`. And this tree never streams: a
repo-wide search for `stream=True` across `eval_awareness_experiments/`,
`models/`, and `probes/` returns exactly one hit —
`models/common/hf_openai_server.py:217`, which *rejects* it with HTTP 400.
`tool_calling_runner.py:265` calls `chat.completions.create(...)` with no
`stream` argument.

The full commit list against that file in the window is seven commits; six are
typing fixes, an assert, or a constructor-signature change (#36049, #36114,
#29184, #38029, #38264, #42570). Only #38168 carries content risk, and only for
streaming.

One narrowing recorded for completeness rather than dismissed: #42570 (v0.21.0)
moved helpers into `vllm/tool_parsers/utils.py`, and in doing so the validity
check went from catching `(JSONDecodeError, ValueError)` to catching only
`JSONDecodeError`. Since the former subclasses the latter this is strictly
narrower, streaming-only, and practically unreachable — but it is a behaviour
change, not a pure refactor.

Related and also inert: `abstract_tool_parser.py` gained an env-gated
structural-tag path that constrains decoding, but
`VLLM_ENFORCE_STRICT_TOOL_CALLING` defaults to `False` (`vllm/envs.py:241` at
v0.23.0) and `get_structural_tag()` is overridden only by the qwen3coder and
deepseekv4 parsers — not hermes. `get_json_schema_from_tools` returns `None` for
`tool_choice="auto"` identically at both tags. No decoding-constraint change
reaches these requests.

#### B7. The Qwen2.5-VL vision tower — changed, but the changed paths are opt-in

Because `opencua.py` subclasses `Qwen2_5_VLForConditionalGeneration`, changes to
`vllm/model_executor/models/qwen2_5_vl.py` reach OpenCUA even though its own
file did not move. **14 commits touched that file in the window.** The ones
carrying numerical weight are both vision-attention backend work:

| PR | Date | Change |
| --- | --- | --- |
| [#34580](https://github.com/vllm-project/vllm/pull/34580) | 2026-02-27 | Adds a FlashInfer/cuDNN backend for ViT attention |
| [#42787](https://github.com/vllm-project/vllm/pull/42787) | 2026-05-23 | Extends FlashInfer metadata support to Qwen2.5-VL vision attention |

Both are **opt-in**. #34580's body says "Enable by
`--mm-encoder-attn-backend=FLASHINFER`", and #42787 fixes an `AssertionError`
that only fires when that flag is already set. The serve scripts do not pass it,
and the default is unchanged:

| Tag | `vllm/config/multimodal.py` | Value |
| --- | --- | --- |
| v0.16.0 | line 134 | `mm_encoder_attn_backend: AttentionBackendEnum \| None = None` |
| v0.23.0 | line 158 | `mm_encoder_attn_backend: AttentionBackendEnum \| None = None` |

The remaining commits are ViT CUDA-graph plumbing (#40830, #41234, #42288,
#42796), GPU↔CPU sync elimination (#42347), compile-cache and naming refactors
(#37345, #36288, #36281, #36063, #38018), a ROCm fix (#43647), and an EVS fix
(#33607). CUDA-graph capture replays the same kernels and should not move
numbers.

**Residual uncertainty, stated rather than smoothed over:** #42796 is titled
"Avoid over-padding Qwen2.5-VL encoder cudagraph window metadata". Padding
changes in an attention path are the kind of thing that *can* alter results if
padded positions are not perfectly masked. We did not read that diff line by
line, and we do not assert it is numerics-neutral. It is a narrow, checkable
follow-up rather than an open-ended one.

#### B8. New tokenizer and detokenizer backends — both opt-in, both off

Two genuinely output-affecting subsystems were added in the window, and neither
is enabled by default:

| Subsystem | Env var | Default at v0.23.0 | First appeared |
| --- | --- | --- | --- |
| Fastokens tokenizer backend ([#41741](https://github.com/vllm-project/vllm/pull/41741)) | `VLLM_USE_FASTOKENS` | `False` (`envs.py:20`) | v0.21.0 |
| Rust frontend / detokenizer | `VLLM_USE_RUST_FRONTEND` | `False` (`envs.py:142`) | v0.22.0 |

Both matter enough to be explicit about, because both would be real hazards if
switched on:

- **Fastokens** is a process-global, irreversible monkeypatch that swaps the
  Rust BPE backend of every HF fast tokenizer loaded afterwards — including the
  `qwen_vl` path these models use. Its equivalence evidence upstream is one
  smoke test. Leave it off.
- **The Rust frontend did not exist at v0.16.0** (the `rust/` directory 404s at
  v0.16.0 through v0.21.0), so "did its default change" is not a meaningful
  question across these endpoints — it has been opt-in since it appeared, and
  v0.23.0's own notes call it "experimental". There is no test asserting
  Rust/Python detokenizer equivalence, and at least one later PR documents a
  divergence, so it should stay off for measurement work regardless.

Note also that the tokenizer thread-safety work
([#41181](https://github.com/vllm-project/vllm/pull/41181), v0.21.0) dispatches
to deep copies of the same tokenizer — same vocab, same merges, therefore
identical token ids. It is a concurrency fix, not a tokenization change.

#### B9. Structured output, TP>1 collectives, MLA, MoE, quantization

`xgrammar` 0.1.29 → 0.2.4 governs guided decoding; no request here sends
`response_format` or a grammar. The allreduce backend change
([#35793](https://github.com/vllm-project/vllm/pull/35793), v0.17.0) requires
TP>1; the serve scripts use `--tensor-parallel-size 1`. FA4-as-default-MLA-prefill
([#38819](https://github.com/vllm-project/vllm/pull/38819), v0.20.0) is
DeepSeek-family MLA, not Qwen attention. The large MoE-oracle refactor series
does not apply to these dense VL models, and no quantization is requested —
`--dtype bfloat16`, matching both repos' `torch_dtype`.

### D. Changed *and changed back* inside the window — the Qwen3-VL deepstack regression

This one deserves its own category, because both a "nothing changed" verdict and
a naive "0.23.0 contains a Qwen3-VL accuracy fix, so numbers moved" verdict get
it wrong.

[PR #43617](https://github.com/vllm-project/vllm/pull/43617) (merged
2026-05-27, shipped v0.23.0) is titled "Fix Qwen3-VL and Qwen3-omni-thinker
accuracy degradation from deepstack inputs under torch.compile". GUI-Owl **is**
a `Qwen3VLForConditionalGeneration`, and this is on the **default** serving
path, not behind a flag.

The mechanism, from the PR body: `_get_deepstack_input_embeds()` returned `None`
when `deepstack_input_embeds_num_tokens == 0`, so during compile warmup the
decoder graph specialised to the no-deepstack path; real multimodal requests
then reused that graph and **the visual deepstack additions were skipped**.

The measured cost, on Geo3K (601 samples) at `temperature=0.0`, `seed=42` —
greedy, so this is not a sampling artefact:

| Config | Qwen3-VL-2B | Qwen3-VL-8B |
| --- | ---: | ---: |
| pre-patch, default compile + cudagraph | **0.2047** | **0.5225** |
| pre-patch, no compile + no cudagraph | 0.2912 | 0.5491 |
| post-patch, default compile + cudagraph | 0.2829 | 0.5657 |

A ~30% relative accuracy drop on the 2B model, purely from serving it the
default way.

**But it is interior to this review's endpoints.** We bisected the faulty early
return across every tag in the window by extracting the body of
`_get_deepstack_input_embeds` from `vllm/model_executor/models/qwen3_vl.py` at
each tag:

| Tags | `_get_deepstack_input_embeds` faulty early-return |
| --- | --- |
| v0.16.0, v0.17.0, v0.18.0, v0.19.0, v0.19.1 | absent — **not affected** |
| v0.20.0, v0.20.2, v0.21.0, v0.22.0, v0.22.1 | present — **affected** |
| v0.23.0 | removed — **fixed** |

(The reporter's environment in the linked bug,
[issue #43602](https://github.com/vllm-project/vllm/issues/43602), was vLLM
0.21.0, consistent with the table.)

The introducing change is
[#40145](https://github.com/vllm-project/vllm/pull/40145), "[Opt] Optimize
deepstack buffer handling for multimodal Qwen3 models", merged 2026-04-25 — two
days before v0.20.0. Its own description names the mechanism: "Track valid
deepstack token spans with `deepstack_input_embeds_num_tokens` so we only fetch
and clear deepstack buffers when they contain active payloads." That tracking is
the early return #43617 removed. An optimisation, not a bug fix, which is why it
went unnoticed for four releases.

**So on this axis the 0.16.0 → 0.23.0 move is net-neutral: both endpoints are
clean.** The regression was introduced at 0.20.0 and repaired at 0.23.0.

Two things follow that matter more than the net-neutral result:

1. **Do not pin to an intermediate version.** Anything in 0.20.0–0.22.1 serves
   Qwen3-VL with degraded visual grounding on the default path. Given the
   floating `vllm>=0.6`, a future re-lock landing on one of those is a real
   possibility.
2. **Any GUI-Owl results collected on 0.20.0–0.22.1 should be treated as
   suspect.** We did not audit `eval_awareness_experiments/experiment_log.md`
   for which vLLM version each historical run used — that is a separate,
   bounded task, and it is the one we would do first.

Note also the honest caveat in the PR's own words: it "does not change the
visual encoder output, sampling configuration, chat template, or request
preprocessing" — the fix restores intended behaviour rather than altering it.

The window contains substantial batch-invariance work (#32561, #37718, #40413,

pre-existing property of both 0.16.0 and 0.23.0, not a regression introduced by
this upgrade — but it does mean this tree has never had run-to-run
reproducibility to lose.

## The CUDA 13 driver surface

`docs/HANDOFF_GUI_OWL_PROBE_RESULTS.md` §3 records that CUDA 13 needs NVIDIA
driver ≥ 580.65.06 and that a mismatch fails **silently** to CPU. The brief asks
whether vLLM 0.23 changes that surface.

**It does not.** vLLM's platform-resolution fallback is byte-identical at both
tags:

```python
else:
    platform_cls_qualname = "vllm.platforms.interface.UnspecifiedPlatform"
    logger.debug("No platform detected, vLLM is running on UnspecifiedPlatform")
```

(`vllm/platforms/__init__.py` at
[v0.16.0](https://github.com/vllm-project/vllm/blob/v0.16.0/vllm/platforms/__init__.py)
and
[v0.23.0](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/platforms/__init__.py).)

That line is `logger.debug`, so the detection step itself is silent at default
log level. But it is **not** the end of the story, and the full answer is better
than "still fails silently".

**`vllm serve` raises. It does not fall back to CPU.** `UnspecifiedPlatform`
carries `device_type = ""`, and `DeviceConfig.__post_init__` in
`vllm/config/device.py` turns that into a hard startup failure:

```python
self.device_type = current_platform.device_type
if not self.device_type:
    raise RuntimeError(
        "Failed to infer device type, please set "
        "the environment variable `VLLM_LOGGING_LEVEL=DEBUG` "
        ...
```

This block is **identical at v0.16.0 and v0.23.0**. So on the "no GPU visible at
all" path, vLLM errors loudly, and **0.23.0 changes nothing about that**.

**But the handoff's failure mode is a different one, and vLLM does not check for
it.** Two verified facts sharpen this:

1. **vLLM detects CUDA through NVML, not through torch.** `cuda_platform_plugin`
   calls `pynvml.nvmlInit()` and checks the device count; it **never calls
   `torch.cuda.is_available()`**. The function is identical at both tags.
2. **There is no driver-version check anywhere in `vllm/platforms/cuda.py`** at
   either tag.

NVML is a driver-level API. On a host whose driver is too old for CUDA 13, NVML
will generally still enumerate the GPUs — so `is_cuda` becomes **True**,
`CudaPlatform` is selected, `device_type` is non-empty, and the `RuntimeError`
above never fires. The failure then surfaces later, inside torch. That is
neither the clean startup error nor the silent-CPU-fallback the handoff
describes.

So the precise answer to the brief's question: **vLLM 0.23.0 does not change
this surface in either direction.** It errors on "no GPU at all" exactly as
0.16.0 did, and it has no driver-floor check in either version. The
`torch.cuda.is_available() → False → loads on CPU` behaviour in
`docs/HANDOFF_GUI_OWL_PROBE_RESULTS.md` §3 is a property of the **probe/HF
path**, which is where it was observed; it is not vLLM's mechanism, and this
review found nothing in vLLM that would reproduce it. **What actually happens to
`vllm serve` on a CUDA-13-incompatible driver remains unverified** and needs one
run on a mismatched host — see [Gaps](#what-i-could-not-determine).

v0.20.0 did switch the default CUDA wheel to CUDA 13.0
([#39878](https://github.com/vllm-project/vllm/pull/39878), bumped to 13.0.2 in
[#40669](https://github.com/vllm-project/vllm/pull/40669) to match PyTorch
2.11.0), which is the same cutover #172 already analysed for `torch`. vLLM's
release notes recommend installing with `--torch-backend=cu129` on hosts at CUDA
12.9.

## Not a numerics finding, but the reason to pin

The locked environment pairs **vLLM 0.23.0 with `transformers` 4.57.5** — a v4
release. vLLM formally deprecated Transformers v4 in
[#40389](https://github.com/vllm-project/vllm/pull/40389) (v0.21.0), whose body
reads in full: "As per deprecation policy."

The deprecation is a single `logger.warning`, still present and still only a
warning at v0.23.0 (`vllm/transformers_utils/config.py:70-75`):

> Support for Transformers v4 is deprecated. The Transformers v4 codepath will
> become unmaintained in vLLM v0.22.0 and will be removed in vLLM v0.24.0.
> Please upgrade to Transformers v5: pip install --upgrade transformers

So the current pairing **works**: no error, no startup gate, v4 branches alive
throughout 0.23.0, and `requirements/common.txt:10` admits 4.57.5. But read the
warning carefully — it says the v4 path became **unmaintained at v0.22.0**,
which the lock is already past, and is **removed at v0.24.0**.

vLLM v0.24.0 was published **2026-06-29**, and the latest release is **0.27.1**
(2026-08-11). `pyproject.toml:100` declares `vllm>=0.6`, which pins nothing. The
only thing holding this environment at 0.23.0 is the lockfile. **The next `uv
lock` that is free to move `vllm` will cross the removal boundary**, at which
point either the `cua` extra breaks, or `uv` drags `transformers` to v5 — and
OpenCUA-32B's remote config/processor code is written against v4
(`transformers_version` in GUI-Owl's config reads `4.57.1`).

This is not a numbers-moving finding. It is the strongest argument that the
extra should carry an explicit upper bound rather than continuing to float.

## What I could not determine

Everything in this note is **source reading**. No vLLM process was executed, no
GPU was involved, and no output was compared. That is the largest single
limitation and it bounds every claim below.

1. **Nothing was measured.** The A2 conclusion — that GUI-Owl's token stream can
   differ between 0.16.0 and 0.23.0 — rests on upstream's own statement that
   FlashInfer output is "statistically equivalent" rather than identical. We did
   not observe a divergence. Conversely, B2's claim that OpenCUA's native
   sampling path is bit-identical is **our reading of the two implementations,
   not an upstream guarantee**, and it has not been executed.

2. **How often the cascade-attention heuristic actually fired at 0.16.0 is
   unknown.** The default moved (A1), but cascade attention was only ever used
   "when the heuristic tells that it's beneficial". Whether it engaged for these
   prompt shapes and batch sizes requires an instrumented run on the old
   version, which is only possible while 0.16.0 is still installable.

3. **`vllm serve` behaviour on a CUDA-13-incompatible driver is unverified.** We
   verified that vLLM raises `RuntimeError` when no GPU is visible, that
   detection is NVML-based, that there is no driver-version check, and that all
   three facts are identical at both tags. What we could **not** establish is
   what actually happens when NVML enumerates a GPU whose driver is too old for
   the CUDA 13 runtime — the case the handoff cares about. Our expectation is
   that it fails inside torch rather than falling back to CPU, but that is
   reasoning about a code path, not an observation. One run on a host below
   580.65.06 settles it, and would let the handoff's §3 be made precise for the
   vLLM path as well as the probe path.

4. **PR #37225's practical effect is genuinely open.** It is labelled `[Perf]`
   but changes the values feeding the pivot-acceptance predicate. It ships **no
   tests** and makes no equivalence claim, so upstream provides no evidence
   either way. We label it "may shift in tie/near-tie cases" rather than assert
   either outcome.

5. **#42796's padding change was not read line by line** (see B7). We do not
   assert it is numerics-neutral for the Qwen2.5-VL vision encoder.

6. **The magnitude of A3 is unquantified**, and the vision-tower commits were
   triaged by title rather than read in full. **30 commits** touched
   `qwen3_vl.py` and **14** touched `qwen2_5_vl.py` in the window. We read the
   ones whose titles indicated accuracy, attention-backend, or kernel-replacement
   work (#37948, #43617, #40145, #40932, #34580, #42787, #38065) and classified
   the remainder — CUDA-graph plumbing, sync elimination, video-timestamp fixes,
   EVS fixes, import and naming refactors — from their titles and release-note
   descriptions. That triage is a judgement call, not a proof. A commit
   mislabelled as a refactor upstream would have been missed.

7. **We did not audit which vLLM version each historical run used.**
   `experiment_log.md` was not cross-referenced against the 0.20.0–0.22.1
   affected range from finding D. This is the highest-value follow-up in the
   note and it is deliberately left as a separate task rather than guessed at.

8. **GUI-Owl's repository could not be read at the path this tree names.**
   `models/common/registry.py:70` declares `xlangai/GUI-Owl-1.5-32B-Think`,
   which returns **HTTP 401** from both the HuggingFace API and the raw file
   endpoint. The model actually exists at **`mPLUG/GUI-Owl-1.5-32B-Think`**,
   which is public, matches `docs/HANDOFF_GUI_OWL_PROBE_RESULTS.md:155`, and is
   the repo whose `generation_config.json` this review used. Every GUI-Owl claim
   here is therefore about the `mPLUG` repo. Whether `xlangai` hosts a private
   fork with different sampling defaults is unknown, and if it does, the A2
   exposure analysis would need redoing against it. **Out of scope to fix here**
   — recorded, not changed.

9. **`--tool-call-parser hermes` against a Qwen3-VL "Think" model was not
   validated end to end.** The parser code is byte-identical on the

   the unified `Parser.parse()` interface introduced in v0.23.0

   source reading settled.

## Recommendation

**The `cua` extra is not safe to leave as-is, but the reason is drift, not
0.23.0 itself. Pin it, then measure once on GPU.**

### 1. Pin `vllm`, and pin it to 0.23.0 specifically

`pyproject.toml:100` currently declares `vllm>=0.6`. That is the actual defect
here — it is why an unreviewed seven-minor-version move could ride in on a
lockfile collapse in the first place, and it leaves the next `uv lock` free to
do it again.

0.23.0 is a *good* place to stop, and the reasons are specific:

- It is the **last release that supports `transformers` v4**, which the lock
  pins at 4.57.5. vLLM's own warning says the v4 path is removed in **v0.24.0**,
  and 0.24.0 through 0.27.1 are already published.
- It is the **first release with the Qwen3-VL deepstack fix** (finding D).
  0.20.0–0.22.1 serve GUI-Owl with degraded visual grounding.

Those two constraints intersect at exactly one release.

**And `transformers` needs a ceiling too — this is the sharpest live risk in the
note.** vLLM 0.16.0 required `transformers <5`; vLLM 0.23.0 relaxed that to
admit **≥ 5.5.1**. The lock currently sits at 4.57.5 only because nothing has
forced it up. Meanwhile
[PR #47438, "[BUGFIX] Fix opencua processor on transformers 5"](https://github.com/vllm-project/vllm/pull/47438),
opened 2026-07-02, is **still open**, and its log shows `vllm serve` on an
OpenCUA model **crashing at startup** under transformers 5. So an unconstrained
resolve can now pull a transformers that breaks OpenCUA outright, where the old
`<5` ceiling made that impossible.

An upper bound on both belongs in the extra:

```toml
cua = [
    "vllm>=0.23,<0.24",
    "transformers<5",
    ...
]
```

Deciding the exact form is a change to `pyproject.toml` and therefore out of
scope for this note — this is the finding, not the patch.

### 2. Measure once, on the one model that is actually exposed

The measurement is small and well-targeted, because the analysis narrowed it to
one model and one axis. On a single H100:

- Serve **GUI-Owl** at 0.23.0 twice — once as-is, once with
  `VLLM_USE_FLASHINFER_SAMPLER=0` — and compare outputs on a fixed task set at
  the production `temperature=0.1`.
- If they agree within noise, A2's practical impact is bounded and the extra can
  ship as-is.
- If they diverge, the same comparison quantifies exactly how much of a
  published GUI-Owl delta is attributable to the sampler rather than to the
  condition under test.

Note the limit established in A2: this isolates the 0.21.0 FlashInfer flip, but
**not** the 0.17.0/0.19.0 Triton masking change, which has no flag. Fully
separating that requires running 0.16.0 side by side — worth doing while it is
still installable, and worth deprioritising if no published result depends on
pre-0.20.0 GUI-Owl runs.

### 3. Do the log audit before either of the above

Cross-reference `eval_awareness_experiments/experiment_log.md` against the
0.20.0–0.22.1 window from finding D. If no GUI-Owl run used an affected version,
finding D closes and the remaining work is just the sampler comparison. If some
did, those results need re-running, and that outranks everything else in this
note.

### What does *not* need doing

- **No `torch`/dtype action.** All dtype selection is explicit `bfloat16`, and
  #172 already established torch 2.11 changes no default dtype, precision, RNG,
  or determinism.
- **No seeding change.** No first-party code calls `torch.manual_seed` or
  `use_deterministic_algorithms`; the seeds present govern dataset sampling.
  vLLM output was never batch-invariant in either version (C5), so there is no
  reproducibility guarantee being broken here — there was none to break.
- **No CI or default-profile action.** `vllm` is absent from the default
  install; ruff, black, mypy and `uv lock --check` are untouched by any of this.
