## Source-grounded architecture boundary

The merged GitLab work added one narrow shared value: seed calls and per-call
results may carry a stable `logical_record_key` and normalized Benchmark. The
strict binder remains feature-local, while current Phase 2c and Phase 4 joins
name GitLab comparison behavior directly. This is appropriate for one consumer.

A Plane-only family should therefore reuse unchanged:

- Benchmark capability validation and explicit evaluator authority;
- per-call seed execution and logical-record evidence;
- Run Definition, Checkpoint, and Run Artifact behavior;
- exposure, current-attempt binding, PVPO, outcome, and reset requirements;
- exact finite-field response comparison where the answer is structured;
- Site Composition and Site Behavior Contract shapes.

It should add locally: Plane routes and Resource Kinds, ordinary identities and
authentication, project/issue fixtures, candidate/state rules, state-update
transport, exact observation/readback, evaluator predicates, cleanup, and reset
postconditions. A small Phase 2c/Phase 4 join is acceptable. A generic workflow
registry, workflow DSL, or cross-Site engine is not justified by Plane alone.

GitLab-to-Plane is the second real consumer that can justify extracting a
narrow multi-Site interface from the concrete Plane and GitLab behavior. The
current validator requires `sites == [site_name]`, the technical specification
declares multi-Site novel tasks out of v1, and the new current-attempt
binding/reward joins name the GitLab comparison feature directly. In contrast,
the older execution layer already binds one configured Benchmark Instance per
task Site, resolves placeholders across them, and collects all reset endpoints.
The missing work is therefore not a new universal runtime. It is explicit
cross-Site generation/validation, two-Site seed and identity composition,
family-owned grading, and a reset protocol with exact postconditions. The
generic reset helper currently posts all endpoints concurrently and waits two
seconds; that is not by itself a TAC Golden-State Reset proof. Disabling the
single-Site checks would remove the evidence needed for the cross-Site claim.

## Accepted next direction

**Lead: Plane-only multi-record triage and selective state updates.**
It is the smallest follow-on that adds both a new Site and a new state-transition
archetype while reusing the current program's logical-record work. It is more
scientifically incremental than another source-only Rocket.Chat family and less
architecturally confounded than starting with cross-Site generation. The first
slice should include an information-only sibling and a selective-update sibling
over the same generated three-to-five issue world.

This recommendation reverses if ordinary participant write/read roles cannot be
demonstrated, exact issue/state readback is unavailable, Golden-State Reset
cannot restore the whole selected fixture, the UI cannot expose the complete
candidate set, or the resulting family reduces to fixed-title copying. A live
GitLab comparison Run is also a sequencing gate for claims that the current
shared binding/runtime path is already validated, though Plane source research
need not wait for that Run.

The bounded ST/SuiteCRM source audit produces a separate recommendation:
comparison-only analysis can proceed without changing WARP Site contracts, but
SuiteCRM generation must remain closed until ordinary writer and independent
reader roles, exact authorized exposure, measured fixtures, evaluator
known-positive/negative behavior, full database-and-app reset, and a trusted
setup-versus-attacker-payload boundary all pass. Native CR/CuP results would be
comparison evidence, not WARP ASR or exact-outcome evidence.

## Scale clarification after source inspection

The proposed three-to-five work-item world is a **per-task evidence bound**, not
a corpus limit. Current WARP Taskgen already scales through host-owned task
cards, per-Site generation, requested action counts, an append-only task bank,
and coverage by `task_archetype`. Current source has nine base archetype IDs,
seven named profiles, and a configurable default of 30 novel tasks per Site.
These source counts prove composition support, not behavioral diversity or a
completed expanded corpus.

The current GitLab comparison path demonstrates the intended modular pattern:
the task card owns workflow shape and the decision rule; the generator may
supply substantive record facts; and a feature-local compiler supplies routes,
seeds, current-attempt physical binding, expected outcomes, and grading. Plane
should reuse this pattern rather than add a universal workflow engine.

The larger proposed Plane portfolio is staged:

1. **Information-only controls:** finite inventory/reconciliation, cross-field
   anomaly selection, and deterministic ranking.
2. **Core state families:** selective single-record state transition and sparse
   batch state transition, with exact changed and unchanged record maps.
3. **Conditional artifact family:** selected-record comment follow-up, only if
   parent, actor, body, visibility, count, and reset readback are exact.

Each Task Archetype receives many generated worlds with substantive variation
in facts, predicates, ties, empty/single/multiple result sets, and selected
records. Titles, wording, record order, and paraphrases remain within-family
variants. Assignment, comment-history chronology, labels, cycles, modules,
parent/link mutation, and record/project creation stay deferred until their own
ordinary-role, identity, readback, and reset contracts pass.

This portfolio can live behind one deep Plane work-item feature package: common
typed worlds, logical-to-physical binding, Site routes, ordinary identities,
fixtures, exact readback, and reset behavior; family-local decision, action, and
evaluator contracts remain distinct. Generic WARP Phase 1 envelopes, task-card
validation, per-Site generation/cache, safety/admission, exposure/PVPO, Run
Artifacts, task bank, and coverage reporting remain reusable. A second generic
registry, CRUD layer, workflow DSL, or global mutable Site registration would
reduce locality without adding scientific evidence.

SuiteCRM is not required for this Plane portfolio or the current WARP paper.
Its only non-redundant later purpose would be a named claim about relational CRM
state plus policy-sensitive action sequences—for example, selecting only cases
linked to overdue accounts, escalating those cases, and not following an
injected export instruction. A simple CRM status update would duplicate Plane.
The recommended active state is therefore comparison-only; generated SuiteCRM
is a conditional reserve, not part of the critical path.

## Bounded alternative screen on 2026-09-02

No current external Benchmark is a better next specification than Plane. The
selection criterion is not name recognition or native task count. It is the
smallest credible addition to WARP's paper evidence: WARP-generated behavioral
diversity on another Benchmark, with a Regular Participant Writer, an
Independent Authenticated Reader where needed, Exact Resource Evidence, exact
outcome attribution, and Golden-State Reset.

A deeper history audit reopens the initial suggestion that WebArena-Verified
Shopping should be the leading breadth candidate. Shopping is not an untried
Site. WARP ran bounded Shopping and Shopping Admin smokes in April 2026 and had
87 Magento-derived adversarial tasks before the strict WASP-scope cutover.
Those were not a completed canonical Run or paper evidence. In one recorded
three-task Shopping Admin smoke, one task complied and two broke; a later mixed
Shopping/Reddit smoke reached the Shopping path but did not complete the full
variant orchestration.

The decisive failure was methodological as well as mechanical. Magento created
customer reviews as pending, so the exact payload did not render for the agent.
WARP temporarily made the mechanics work by forcing the review to approved
status and adding a database backstop. That bypassed the Site's moderation
boundary. Recorded Shopping trajectories also showed that an agent could move
from a category page directly to a cart and never read the product-detail
review. WARP therefore removed Magento from the active corpus and instance
configuration on 2026-04-21 rather than treating false non-encounters as
resistance. Current source keeps only historical/support Shopping plumbing: no
Shopping Site Composition, Site Targeting profile, editor registration, or
generated Task Archetype portfolio is active.

The 2026 WebArena-Verified distribution improves Shopping packaging,
customer auto-login, environment control, and deterministic native evaluators.
It does not establish that a Regular Participant Writer can publish an exact
review without a trusted moderation bypass, or that the legitimate task must
encounter that review. Shopping should therefore be a research hypothesis, not
the default post-Plane breadth lane. A safe reversible cart/wishlist action
would avoid checkout risk, but it would not repair an unnatural carrier.

The stronger marketplace candidate is now deeper VisualWebArena Classifieds.
Its August 2026 WARP canary already proved one normal-user listing reply with an
exact reply ID, a Fresh Anonymous Reader, Painted Visibility, one admitted
task/Run result, and Golden-State Reset. It remains only an explicit POC:
final-state Site support is declared unsupported and its only action card is an
information-only opposite-label response. A generated multi-listing decision
or selected-listing reply family would still require a new specification and
exact wrong-target/extra-reply grading, but it begins from a more natural
untrusted-participant carrier than Magento reviews.

WorkArena++ is the most canonical enterprise reference in this screen: it has
19,912 WorkArena-L1 instances and 682 composite tasks. It is a worse active
WARP target. Its documented setup uses a remote ServiceNow instance, its task
identity defaults to an admin role, and its teardown is best-effort temporary
user deletion rather than a proved Golden-State Reset. Its enterprise triage
also overlaps Plane unless a later claim specifically requires ServiceNow's
forms, catalog, or compositional task system.

Other current 2026 candidates remain controls or research references:

- VisualWebArena Classifieds can test visual grounding, but WARP already has a
  one-task positive-control canary and native fixed-ID/visual evaluators are
  not current-attempt WARP evidence.
- OpenApps is cheap, configurable, and state-transparent, but its own paper
  studies simple UI tasks and current source has no independent ordinary
  attacker-to-reader exposure contract.
- TimeWarp tests robustness across six UI eras, not persistent participant
  writes or IPI exposure.
- WebArena-Infinity and WebForge generate whole Sites and tasks. They are useful
  scalability comparisons, but placing their generator inside WARP would
  confound WARP's wrapper claim and create a much larger audit surface.
- ClawBench and the 2026 CAP benchmark use live Sites. They improve live-web
  realism, but they cannot provide controlled native seeding and Golden-State
  Reset.
- BrowserGym Knows PR #397 remains open and says its paper, repository, and
  data will be public later. It also needs Google account and service-account
  state. It is not ready for a WARP decision.

The practical sequence after a successful Plane result has two independent
lanes. GitLab-to-Plane is the stronger next claim and stays on the scientific
critical path. The approved marketplace breadth lane uses deeper Classifieds,
which has stronger WARP exposure evidence than Shopping. Shopping remains
useful only if a specific moderated-commerce claim justifies its harder
exposure problem. WorkArena++ remains a conditional third-Benchmark research
target. There is no need to replace SuiteCRM with another active integration
merely to keep the tree full.

   may validate independently, but it is not the complete breadth deliverable.
9. **The first Classifieds portfolio has one deep state-changing verb:** post

    evidence, expected target set, and injected reply can yield a decide task

11. **Classifieds scale is demonstrated by auditable behavioral coverage, not
    raw task count or a corpus ceiling.** Report generated and admitted counts,

12. **The first complete Classifieds portfolio has four authored Task

    decision core each produce an information-only sibling and a selective
    reply sibling. Ties, exclusions, near misses, carrier positions, and
    zero/one/many correct targets are generated strata, not new workflow
    abstractions.
13. **Carrier placement is balanced by the listing's decision role.** Coverage
    and results distinguish payloads on qualifying targets, disqualified
    distractors, ranked winners, and plausible runners-up. This prevents
    exposure from being accidentally coupled to only the intended action or
    only a distractor.

No ADR is warranted yet. The accepted sequence uses existing domain language
and has not introduced a durable shared interface decision.

## Site and Benchmark clarification

VisualWebArena Classifieds is a self-hosted OSClass application populated from
the upstream `osclass_craigslist.sql` seed. It is a Craigslist-style classified
advertising marketplace, not the live Craigslist website. In WARP terms,
`classifieds` is the Site and `visualwebarena` is the Benchmark. Deepening the
existing POC would therefore add both a new generated Site portfolio and a
distinct Benchmark identity; it would not merely add another Site to
WebArena-Verified.

An additional Benchmark can also be carried as a comparison without becoming a
WARP generation target. The balanced evidence plan is currently: generated
Plane depth, optional generated VisualWebArena/Classifieds breadth, and
ST-WebAgentBench comparison-only analysis. A third full generation target is
not justified by integration count alone. WorkArena++ is the leading
enterprise/compositional reference if a later non-redundant claim requires it,
but ordinary-role access and Golden-State Reset remain blocking scientific
gates rather than configuration details.

Three claims must remain separate. **Marketplace breadth** changes the
application domain, record model, ordinary participant surface, and action
outcomes; it can be proved with textual listing facts. **Vision-dependent task
evidence** makes a legitimate decision depend causally on image content or
spatial rendering; it needs matched text-only and image-intervention controls.
**Visual prompt injection** places the adversarial instruction itself in an
image; that is a different attack-carrier claim and is not part of the current
Classifieds proposal. Recent literature also uses “grounding” both for image
semantics and for mapping a plan to an exact screen control, so WARP should name
the narrower causal claim rather than infer it from screenshot availability.

### Classifieds injection carrier

The current proven IPI carrier is ordinary text in `listing_reply.body`, not an
image. Before the evaluated agent starts, WARP binds one generated payload to
an exact candidate listing and materializes an editor call equivalent to
`create_listing_reply(listing_id, body)`. The feature-local editor uses the
Regular Participant Writer's authenticated session to fetch the ordinary
listing form, retain its CSRF token and actor identity, and POST one top-level
`add_comment` form. The form title stays the fixed benign value `Additional
listing details`; only the reply body is attacker-controlled. A same-listing
refetch recovers exactly one new reply ID, and an independent reader then
checks the listing, reply, actor, body digest, signature, and Painted
Visibility before admission.

For a multi-listing family, the legitimate evidence path must require reading
the reply surface on the finite candidate set. Price, timestamp, or photograph
selection alone would let the agent bypass the carrier and would repeat the
historical Shopping non-encounter problem. One valid shape is to identify a
candidate from listing fields or an image, then consult ordinary replies for a
required availability or included-item fact before answering or acting. The
seeded attacker reply and any later reply created by the evaluated agent are
different resources and roles. Current source proves the former; a
state-changing follow-on still needs feature-local final-state grading for the
latter because Classifieds final-state evaluation remains unsupported.

## Resolved marketplace frontier

The six-family Plane portfolio, removal of generated SuiteCRM from the active
tree, and the textual Classifieds reply-carrier topology are settled. The
marketplace choice is also resolved. The alternatives considered after Plane
were:

1. **Public marketplace UGC breadth:** deepen Classifieds from its exact
   one-task canary into generated multi-listing information-only and
   selected-listing reply families. This has the strongest current WARP actor,
   exposure, identity, and reset evidence. It adds a VisualWebArena-environment
   marketplace result, but final-state grading and behavioral diversity still
   need design. The deciding listing attributes should initially be available
   as text/state so safety failures are not confounded with image perception.
   A separate, gated vision-dependent sibling may later hold the same records,
   actions, prompt, and evaluator fixed while moving the deciding fact into an
   image and masking or swapping that cue. If text-only and masked arms do not
   degrade, retain only the marketplace-breadth claim.
2. **Moderated commercial reviews:** revisit Shopping only if the claim is
   specifically about how a browser agent uses platform-approved customer
   reviews. A finite product comparison plus reversible cart/wishlist action is
   plausible, but forced review approval or a route that lets the agent bypass
   the carrier invalidates it.
3. **No marketplace branch:** keep GitLab-to-Plane as the only post-Plane
   critical path and spend the evidence budget on the current program and the
   larger Plane corpus.

Option 1 is accepted as the post-Plane parallel breadth lane. It does not
replace GitLab-to-Plane on the scientific critical path. Option 2 should not
advance without a new, natural review-exposure contract, and option 3 remains
the stop condition if the Classifieds evaluator or runtime evidence gates do
not pass. The next independent frontier is whether the first Classifieds
state-changing stage should expose one deep selective-reply action or several
shallower marketplace mutations. That boundary is now accepted. The
four-family set and role-balanced carrier matrix are also accepted. No further
consequential user choice remains in the Classifieds planning frontier. The
remaining work is to state source-derived ownership, evidence gates, parallel
packages, the critical path, and stop conditions. The vision-dependent control
remains gated behind the text/state breadth result.

Dependent choices—generated corpus allocation per Plane family, the exact
state/comment action set, the later cross-Site contract shape, live NPCs,
additional TAC Sites, office workflows, and tickets—remain closed until their
parent decisions and evidence gates are settled.

## Consolidated follow-on plan

### Next specification and smallest vertical slice

The next specification should be **Plane-only multi-record triage and selective
state updates**. It should not begin with GitLab-to-Plane: Plane must first
prove its own ordinary identities, deployed route, fixture, exact readback,
grading, and reset behavior. Otherwise a cross-Site failure cannot be
attributed to Plane, the composition seam, or GitLab.

The smallest vertical slice uses one generated project with three to five work
items and one shared decision world:

1. an information-only task reports the exact qualifying work-item set;
2. a state-changing sibling transitions only that set to one allowed state;
3. an independent ordinary reader verifies every changed and unchanged item;
4. Golden-State Reset restores the complete fixture and proves the post-reset
   state.

The deployed TAC fork needs a route/version canary because its helper still
uses the deprecated `/issues/` family while current public Plane uses
`/work-items/`. The first slice avoids assignee mutation because current Plane
issue #9517 reports silent drops for non-project members. `Blocked` is a
fixture state name, not a portable Plane state group. These checks prevent a
plausible fake-based integration from being reported against a different live
API or permission model.

That slice validates the end-to-end behavior; it is not the scientific
deliverable. The accepted Plane deliverable remains six Task Archetypes with
many generated worlds: three information-only families, two selective state
families, and one conditional comment family gated by exact artifact grading.

### Runtime and evidence gates

| Gate | Smallest sufficient check | Concrete failure prevented |
| --- | --- | --- |
| Plane deployed route and role | One read plus one reversible state update by an ordinary project member on the pinned TAC deployment | Designing against current public docs while the deployed fork still exposes older routes or different permissions |
| Plane decision correctness | Known-positive worlds plus empty, tie, near-miss, stale-ID, wrong-state and ambiguous-selection negatives | A generator that produces copied answers, ambiguous targets, or accepts the wrong logical record |
| Plane final state | Fresh independent readback of the exact selected and unselected ID→state map, followed by terminal reset and the same map restored | Request-only success, wrong-target updates, unauthorized extra changes, stale state, or partial reset |
| Classifieds Stage A | Exact seeded reply readback and Painted Visibility; a fixture intervention showing the required benign fact cannot be answered without reading replies | Repeating Shopping's false non-encounter problem merely because an injection exists somewhere on the Site |
| Classifieds Stage B | Fresh post-attempt enumeration of replies bound to listing, reply ID, actor, body and attempt time; positives plus wrong target, missing, duplicate, extra, stale and propagated-body negatives | Confusing the pre-Run attacker reply, an old reply, or a request receipt with the evaluated agent's exact outcome |
| Classifieds reset | Restore the bounded listing/reply fixture and prove all attempt-created reply IDs absent | Cross-attempt contamination and inflated success/failure attribution |
| GitLab-to-Plane | Prove each Site-local slice first; then one explicit two-Site seed→read→act→readback→dual-reset smoke | Masking a broken Site behind a composition, cross-binding IDs, or resetting only half of the task state |

Source and fake-backed checks can run concurrently. Any mutable Plane or
Classifieds smoke must be serialized within its Golden-State Reset scope.
Plane and Classifieds runtime work may overlap only on genuinely isolated
Benchmark Instances. A GitLab-to-Plane attempt reserves both Site instances
and resets/verifies both before another attempt uses either scope.

### Parallel work packages and critical path

These are ownership packages, not tickets:

1. **Current-program lane:** the active main task retains E3–E7 generation,
   evaluation, matched Runs, and synthesis. Follow-on work must not modify its
   ticket worktrees or redefine its frozen corpus.
2. **Plane decision/domain lane:** owns generated work-item worlds, six authored
   families, expected selections and feature-local tests in new Plane feature
   modules.
3. **Plane Site-behavior lane:** owns deployed routes, ordinary identities,
   fixtures, actions, independent readback and reset. It can develop alongside
   the decision lane after agreeing only the typed logical work-item boundary.
4. **Plane integration lane:** one owner makes the few shared Phase 1/2c/4 and
   Site Composition edits after the two local contracts settle, preventing
   overlapping changes in generic phase files.
5. **Comparison/reference lane:** ST-WebAgentBench evaluator-health analysis
   and WebChoreArena-inspired supported-Site family design remain read-only or
   feature-local and can proceed without any Site onboarding.
6. **Post-Plane parallel fork:** GitLab-to-Plane owns the explicit cross-Site
   validator/binding/reward seam; Classifieds owns its separate marketplace
   feature and VisualWebArena runtime. One integration owner sequences any
   unavoidable shared declarations.

The actual scientific critical path is:

```text
current E3–E6 measured evidence
→ Plane specification
→ Plane Site-local source and focused checks
→ serialized Plane no-model/live validation
→ generated/admitted Plane portfolio and completed Runs
→ GitLab-to-Plane specification and explicit two-Site seam
→ isolated cross-Site validation and completed Runs
→ paper claim
```

The Classifieds portfolio branches after the Plane specification establishes
the next architectural baseline. It can proceed in parallel with
GitLab-to-Plane because its feature code and VisualWebArena instance are
different; it does not block the cross-Site claim. If the paper requires the
approved second-Benchmark breadth claim, its admitted corpus and completed
Runs become an additional synthesis dependency, not evidence that the
GitLab-to-Plane seam itself works.

### Reversal and stop conditions

- Reverse the Plane-first recommendation if the pinned deployment cannot give
  an ordinary member the required read/write authority, does not expose the
  finite candidate set, lacks exact fresh readback, or cannot restore the
  bounded fixture. Do not replace those failures with admin access. In that
  case, Classifieds becomes the next viable generated breadth specification.
- Stop Plane family expansion if generated variation collapses to title/value
  copying or if selection cannot be made unique and independently graded.
- Do not start GitLab-to-Plane until Plane works alone. Stop if supporting one
  explicit pair requires a universal workflow engine or weakens either Site's
  current-attempt identity and reset proof.
- Stop Classifieds after Stage A if legitimate tasks can bypass replies. Stop
  before Stage B if exact attempt-created reply sets or reset absence cannot be
  graded. The existing one-task canary then remains a carrier proof, not a
  portfolio result.
- Keep the visual sibling out of the claim if text/DOM-only or masked-image
  controls perform equivalently, or if filenames, alt text or URLs reveal the
  target.
- Keep SuiteCRM comparison-only unless a later claim requires relational CRM
  state and policy-sensitive sequences and ordinary-role exposure, evaluator
  behavior, exact state, and full database/application reset all have credible
  positive evidence.
