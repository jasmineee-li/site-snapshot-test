# Own generated workflows by concrete feature

New behavioral families own their generated factual-content schema, decision
rule, consistency checks, seed recipe and expected-result construction in a
concrete feature module. The first GitLab comparison feature and the first
Rocket.Chat conversation feature compile into existing task, Site, seeding,
admission, action and reward interfaces; those existing owners keep routing,
ordinary-participant writes, exposure, scoring and safety policy. Shared seams
grow only for behavior both concrete features actually require, such as explicit
Benchmark identity, logical-record-to-resource binding and independent-reader
context. This keeps task coherence local without duplicating safety logic.

## Considered options

- Add workflow-specific branches throughout generic Phase modules. Rejected
  because a change to one family would be scattered across callers.
- Introduce a universal workflow DSL, registry or engine first. Rejected because
  the two known families do not justify that interface and would have to encode
  Site and reward behavior that already has an owner.
- Let each benchmark integration copy generation, admission and evaluation.
  Rejected because it would make the transfer claim depend on parallel safety
  implementations.

## Consequences

Generated content is constrained but substantive: WARP may generate factual
relationships and their natural presentation, while host-owned family behavior
derives the answer/action and rejects inconsistent content. The generator never
authors routes, runtime resource IDs, evaluators or cleanup. Some small feature
implementations may resemble one another initially; a shared protocol is
extracted only after two real consumers demonstrate the same need.
